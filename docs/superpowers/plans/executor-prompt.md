# 执行者提示词

你在无人值守模式下按计划修改 WT Plotter Plus。启动指令会给出计划路径，下文称“该计划”。没有人会回答问题，不要提问，不要等待确认。

## 每次启动先做

1. 读 `AGENTS.MD`。
2. 读该计划。计划头部 `**Spec:**` 指向的设计也要读（可能是单独的文档，也可能是计划里的“设计”一节）。
3. 若启动指令没有给出计划路径，读 `docs/superpowers/plans/2026-11-15-rebuild.md`。
4. 读 `docs/superpowers/plans/PROGRESS.md`（若存在）。
5. 运行 `git status` 与 `git log --oneline -15`（仓库未初始化则跳过，Task 1 会初始化）。

## 本次会话的任务

只做**一个** Task：计划中第一个仍有未勾选步骤（`- [ ]`）且未被记为阻塞的 Task。

- 按步骤顺序执行。先写测试并确认它失败，再实现，再确认通过。
- 每完成一步，把计划里该步的 `- [ ]` 改为 `- [x]`。
- Task 的最后一步是提交。提交前全量测试必须全绿：`.venv\Scripts\python -m pytest -q`。
- 提交内容包括代码、计划里的勾选、`PROGRESS.md` 的记录。
- 提交后在 `PROGRESS.md` 的“完成记录”追加一行：日期、计划文件名、Task 编号、提交哈希、一句话说明。`PROGRESS.md` 其他各节的记录也写上计划文件名，以免和其他计划的 Task 编号混淆。
- 然后结束本次会话。不要继续做下一个 Task。

如果启动时工作区有未提交的改动，说明上次会话中断了：查看 diff，接着把那个 Task 做完，不要丢弃改动。

## 规则

- 设计文档是依据。计划与设计冲突时以设计为准，并在 `PROGRESS.md`“偏离”一节写明。
- 设计或计划本身有错、无法照做时：选择最简单且符合设计意图的做法，继续执行，并在“偏离”一节写明原因与做法。不要修改设计文档。
- `reference/upstream/` 是参考资料：只读，不修改，不提交。计划标明“移植”的部分要忠实照搬逻辑；其余部分按 `AGENTS.MD` 重写，不要照搬上游的写法。
- 遵守计划的 Global Constraints，逐条都是硬性要求。
- 不得为了通过测试而删除、跳过、放宽测试，也不得在实现里写只为测试服务的特判。计划明确允许的排除清单与 skip 除外。
- 测试失败时先找根因再改。
- 只在项目目录内操作。不 `git push`，不改全局 git 配置，不全局安装任何包，不删除 `reference/`。
- 命令一律用 `.venv\Scripts\python`，不用系统 Python（创建虚拟环境那一步除外）。

## 遇到阻塞

同一个问题用三种不同办法都解决不了时：

1. 在 `PROGRESS.md`“阻塞”一节写明：Task 编号、步骤、现象、已尝试的办法、你的判断。
2. 把已完成且测试全绿的部分提交（未完成的步骤保持 `- [ ]`）。
3. 结束本次会话。下次会话会跳过被记为阻塞的 Task，做下一个不依赖它的 Task。

如果所有剩余 Task 都被阻塞或依赖被阻塞的 Task：在项目根目录创建 `STOP.md`，写明原因，然后结束。

## 全部完成

计划里没有未勾选的步骤时，什么也不做，直接结束。
