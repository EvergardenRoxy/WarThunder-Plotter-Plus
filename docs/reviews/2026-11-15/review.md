## R01 · P1 · 大量历史位置触发参数上限，游标与时间轴停止更新

位置：`wt_plotter/web/static/viewer.js:216–231`，重点为第 223 行。

`Math.max(...processed.map(...))` 将每个位置的时间戳作为独立函数参数。历史页面首次请求返回整场位置，记录量达到引擎上限就抛出 `RangeError`。此时数组已经追加，但游标、最大时间和正常渲染步骤都未完成。实时页面后续又从旧游标请求，可能反复追加同一批数据。

复现：一次返回 200,000 条位置，结果为 `RangeError`、`lastTimestamp=0`、`maxTimestamp=0`、正常 `_render()` 调用次数为 0。构造函数中的其他渲染入口仍可能显示部分画面，因此不能简单等同于“画面必定永久空白”。

这不是必须录制数小时才会出现的数量级：按理想 5 Hz、平均 40 个对象估算，约 17 分钟即可达到 20 万条；实际采样频率与对象数量会影响达到时间。具体报错阈值因引擎而异。

建议：在遍历位置时累积最大时间戳，取消展开调用。增加一次加载大记录量的行为测试。

## R02 · P2 · 重叠轮询重复追加位置

位置：`wt_plotter/web/static/viewer.js:179–185,216–225,240–245`。

每 500 ms 无条件发起新请求，不等待前一个 `_loadPositions()` 完成。慢请求或首次加载较多历史数据时，两个请求会使用同一个 `lastTimestamp`。返回后直接追加，未按已有位置 ID 排除重复。

复现：并发调用两次实际 `_loadPositions()`，请求 URL 相同；后端各返回同一条 `id=0` 的位置，最终数组长度为 2、唯一 ID 数量为 1。

影响：轨迹重复绘制、统计偏大、额外内存占用；响应乱序时，依赖数组末尾为最新位置的统计也可能显示旧信息。

建议：让位置轮询串行完成后再调度下一次，保持单个在途请求；优先用这一简单方案消除源头，不先添加多层重试机制。

## R03 · P2 · 第二个采集器把正在采集的比赛当成遗留比赛关闭

位置：`wt_plotter/capture/capturer.py:52–55,67–69`；`wt_plotter/storage/db.py:335–341`；`wt_plotter/cli.py:38–47,89–97`。

单实例检查仅检查当前 Web 端口。两个 `capture` 进程，或使用不同端口的两个 `watch`，都能访问同一个默认数据库。每个采集器启动时都会关闭数据库内所有未结束比赛，没有区分另一个仍在运行的采集器。

复现：两个 `Capturer` 用同一临时数据库按顺序运行；第二个启动后，第一个比赛已经有 `ended_at`。第一个继续 tick，仍向这场“已结束”比赛写入，位置数由 1 增至 2。

影响：比赛提前结束、记录分裂。网页还会允许删除这场实际上仍在写入的比赛；若用户删除，旧采集器后续写入将违反外键约束。

建议：把单采集器所有权绑定到数据库/数据目录，并覆盖 `watch`、`capture` 两个入口。网页服务本身仍可独立读取数据。回归场景应包含两个采集入口使用同一数据库。

## R04 · P2 · 空中切回地面时，第一帧地面坐标被再次换算

位置：`wt_plotter/capture/tracker.py:118–121,134–145,160`。

占领点坐标变化 `poi_changed` 被直接当作空中视角证据。空中地图切回地面时，占领点坐标同样变化，即使 `army=tank`，也会将该 tick 标记为空中视角，并套用已有的空中到地面变换。

复现：地面 → 缩放为 0.25 的空中视角 → 原地面坐标。返回地面的 tick 为 `is_player_air=0`、`is_player_air_view=1`，原 `x=0.8` 被换成 `x_ground=2.8`。

影响：产生落在地图外或明显错误的位置。通常下一帧恢复，但错误坐标已经写入数据库，历史回放也会受影响。

建议：区分进入空中和返回地面的方向，不能单凭“坐标发生变化”判定空中视角。针对往返转换而不只是单向转换添加回归测试。

## R05 · P2 · 先出现占领点，会永久丢弃后出现的出生点

位置：`wt_plotter/capture/tracker.py:148–158`。

任意 POI 写入后都会设置 `poi_captured=True`；后续所有非占领点 POI 都被跳过。这不能表示“所有出生点都已收齐”。

复现：第一帧只有 `capture_zone`；第二帧保留占领点并新增 `respawn_base_tank`。数据库内出生点记录数始终为 0。

影响：分帧到达的出生点、后出现的机场等静态标记不会进入回放。这也影响刚加入比赛时尚未完整加载对象的情况。

建议：按静态 POI 的标识或位置记录已经保存的对象，不使用“出现过任意 POI”这个全局布尔值替代去重。

## R06 · P2 · 纯空战位置被显示过滤器全部隐藏

位置：`wt_plotter/web/static/viewer.js:386–391`；`wt_plotter/capture/tracker.py:134–138,167–170`。

显示过滤器无条件隐藏 `type=aircraft`，并隐藏所有没有 `x_ground` 的空中视角位置。纯空战从空中视角开始，没有前一帧地面对象可供拟合；原始坐标本来对应本场空战地图，却被当作“缺少地面换算”过滤。

复现：玩家飞机对象被隐藏；将同一空中 tick 的对象改为占领点，仍因 `x_ground=null` 被隐藏。结果不依赖筛选框是否勾选。

这是当前代码和上游查看器共同存在的功能限制，不应称为本次重建新增回归。如果产品有意只支持地面轨迹，应明确写入支持范围；当前 README 没有这一限制说明。

建议：将本场地图坐标系与陆战中的空中支援视角区分开。空战地图上的原生坐标无需强制转成地面坐标。

## R07 · P2 · 结束状态先到达时，不再补拉最后一批位置

位置：`wt_plotter/web/static/viewer.js:240–245,255–267`。

位置和状态是独立请求。可以出现：位置请求已经读到旧快照 → 采集器提交最后一个 tick 并结束比赛 → 状态请求读到 `ended_at`。此时设置 `isLive=false`，后续轮询不再读取位置，没有最终补拉。

复现脚本使用实际 `_startPolling()` 回调，模拟位置快照返回 1 条、随后服务端提交第 2 条并返回结束状态。执行下一次轮询后，服务端仍有 2 条、查看器只有 1 条，位置请求总数仍为 1。该测试使用可控响应顺序，不是实际网络时序压力测试。

影响：当前页面缺少末尾轨迹，刷新历史页面后才恢复；若页面恰好在最后一帧后才打开则不会触发。

建议：在结束状态下等待现有位置请求完成，再按更新后的游标补拉一次，之后切换显示状态。与 R02 的串行轮询一起处理。

## R08 · P2 · 先启动 serve 后启动 watch，不会开始采集

位置：`wt_plotter/cli.py:31–35,42–47`。

已有 `/api/status` 返回成功就直接打开网页并退出，完全不检查已有服务的 `capturing` 状态。用户先用 `serve` 查看历史，再运行默认命令或 `watch`，看起来进入实时页面，实际仍然没有采集器。

复现：模拟已有服务探测成功，以 `capture_enabled=True` 调用 `_run_web_mode()`；`Capturer` 完全没有被创建。

建议：区分已有服务是只读模式还是采集模式。最小处理可以是明确报出“已有 serve，需先关闭或另启 capture”，避免静默成功；是否自动提升服务模式属于后续产品决定。

## R09 · P2 · serve 模式把空战状态报告为坦克

位置：`wt_plotter/web/app.py:153–168`。

没有内置 capturer 时先将 `army` 设成默认值 `tank`；查询到真实 tick 后又用 `army or tick.army_type`，默认值永远覆盖实际兵种。独立 `capture` 配合 `serve` 时，显示的兵种会错误。

复现：临时数据库最新 tick 为 `army_type=air, vehicle_type=test_plane`；实际 `/api/status` 返回 `army_type=tank, vehicle_type=test_plane`。

建议：先选择信息来源：有本地采集器则读采集器，否则读最新 tick。只有来源没有数据时才应用默认值。

### A02 · 首帧地图下载失败后，没有有效 tick 内的补取

`wt_plotter/capture/tracker.py:50–56` 仅开局时抓取地面图片。若第一次网络超时，之后保持有效地面 tick，则整场 `map_hash` 为空、地图接口为 404。现有设计明确允许“没有图片也开始未知地图比赛”，因此这是已接受行为中缺少恢复的一点，不作为违背设计的回归。是否补取需与真实游戏接口表现一起确认。

### A03 · 异常遥测响应会结束采集线程

`wt_plotter/capture/client.py:17–30` 的 JSON 解析在请求异常处理之外；`capturer.py:52–58` 没有恢复这类边界错误。无效 JSON、错误字段类型或非法图片会传播到线程，记录错误后停止采集。代码路径明确，但本次没有真实响应证明游戏会产生这些格式。若后续抓到样本，应只在遥测边界处理具体可恢复错误，不为此增加全局 `except Exception` 或重复判空。
